# Инкапсуляция и соглашения об именовании

> **Главная мысль.** У класса есть **публичный интерфейс (public API,**
> *Application Programming Interface* — **программный интерфейс приложения)** —
> атрибуты и методы, через которые пользователь должен взаимодействовать с
> классом и его экземплярами. Остальное — **детали реализации**, которые могут
> измениться в любой момент. В Python нет спецификаторов доступа, запрещающих
> обращаться к деталям реализации. Вместо них используются соглашения об
> именовании: имя с префиксом **`_`** объявляет объект служебным, а для имени
> с префиксом **`__`** интерпретатор дополнительно выполняет **искажение имени
> (name mangling)**. Соблюдение соглашений интерпретатор не проверяет, и
> возможность доступа к атрибутам они не ограничивают. Ответственность за
> добросовестное использование API лежит на пользователе кода.

---

## 1. Публичный интерфейс и детали реализации

**Инкапсуляция** — это объединение состояния и поведения в объекте и сокрытие
деталей реализации от кода, который этот объект использует. Первую часть мы
уже применяли: класс объединяет атрибуты и методы. Теперь рассмотрим вторую
часть.

В следующем примере счет хранит историю операций, а баланс вычисляется по ней:

```python
class BankAccount:
    def __init__(self, owner: str) -> None:
        self.owner = owner
        self.operations = []

    def deposit(self, amount: int) -> None:
        self.check_amount(amount)
        self.operations.append(amount)

    def withdraw(self, amount: int) -> None:
        self.check_amount(amount)

        if amount > self.get_balance():
            raise ValueError("insufficient funds")
        self.operations.append(-amount)

    def get_balance(self) -> int:
        return sum(self.operations)

    def check_amount(self, amount: int) -> None:
        if amount <= 0:
            raise ValueError("amount must be positive")


account = BankAccount("Alice")
account.deposit(100)
account.withdraw(30)
print(account.get_balance())  # 70
```

По замыслу автора атрибуты и методы этого класса делятся на две группы:

| Группа | Имена | Назначение |
|---|---|---|
| **Публичный интерфейс** | `owner`, `deposit`, `withdraw`, `get_balance` | предназначены для использования вызывающим кодом |
| **Детали реализации** | `operations`, `check_amount` | выполняют служебные функции внутри класса и не предназначены для прямого использования |

Метод `check_amount` нужен только для того, чтобы не повторять одну и ту же
проверку в `deposit` и `withdraw`. Список `operations` — выбранный автором
класса способ хранить состояние счета.

## 2. Проблема: интерфейс не отличить от деталей реализации

Деление на две группы известно автору класса, но в коде оно никак не выражено.
Все имена выглядят одинаково, и пользователь не может определить, на какие из
них можно полагаться. Ничто не подсказывает, что вызывать `deposit` следует, а
изменять список `operations` напрямую — нет.

Между тем такое изменение позволяет обойти проверки. Методы `deposit` и
`withdraw` гарантируют, что суммы положительны, а баланс не становится
отрицательным. Эти гарантии действуют, только пока состояние изменяется через
публичные методы:

```python
account.operations.append(-1000)
print(account.get_balance())  # -930 -- проверки не выполнялись
```

## 3. Соглашение об именовании: одно подчеркивание

В C++ и Java для разделения интерфейса и деталей реализации существуют
**спецификаторы доступа** (`private`, `protected`, `public`), и обращение к
закрытому члену класса является ошибкой компиляции. В Python такого механизма
нет: все атрибуты объекта доступны любому коду. Намерения разработчика
выражаются **соглашениями об именовании**.

Имя, начинающееся с **одного подчеркивания**, объявляет объект **служебным**,
или **непубличным (non-public)**. Перепишем класс: добавим подчеркивание к
именам, относящимся к деталям реализации.

```python
class BankAccount:
    def __init__(self, owner: str) -> None:
        self.owner = owner
        self._operations = []

    def deposit(self, amount: int) -> None:
        self._check_amount(amount)
        self._operations.append(amount)

    def withdraw(self, amount: int) -> None:
        self._check_amount(amount)

        if amount > self.get_balance():
            raise ValueError("insufficient funds")
        self._operations.append(-amount)

    def get_balance(self) -> int:
        return sum(self._operations)

    def _check_amount(self, amount: int) -> None:
        if amount <= 0:
            raise ValueError("amount must be positive")


account = BankAccount("Alice")
account.deposit(100)
account.withdraw(30)
print(account.get_balance())  # 70
```

Поведение класса не изменилось, но теперь по именам видно, что `owner`,
`deposit`, `withdraw` и `get_balance` образуют публичный интерфейс, а
`_operations` и `_check_amount` относятся к деталям реализации. Подчеркивание —
это сообщение разработчика класса пользователю:

- объект является деталью реализации;
- обращаться к нему из кода вне класса не следует;
- поддержка не гарантируется: объект может измениться или исчезнуть без
  предупреждения.

Это **только соглашение**. Интерпретатор не обрабатывает такие имена особым
образом и доступ к ним не ограничивает. Внутри самого класса служебные имена
используются без ограничений: именно для этого они и предназначены.

## 4. Два подчеркивания в начале имени

Если имя в теле класса начинается с **двух подчеркиваний** и не заканчивается
двумя подчеркиваниями (`__balance`), интерпретатор изменяет его. Этот
механизм называется **name mangling**: имя `__balance` в классе `BankAccount`
заменяется на `_BankAccount__balance`.

```python
class BankAccount:
    def __init__(self, balance: int) -> None:
        self.__balance = balance

    def get_balance(self) -> int:
        return self.__balance


account = BankAccount(100)
print(account.get_balance())  # 100
print(account.__dict__)       # {'_BankAccount__balance': 100}
print(account.__balance)
# AttributeError: 'BankAccount' object has no attribute '__balance'
```

Несмотря на замену, в теле класса, а также в методах, определенных в теле
класса, обращаться к атрибуту по исходному имени по-прежнему допустимо:
интерпретатор автоматически подставляет вместо него фактическое имя
`_BankAccount__balance`. Поэтому метод `get_balance` может использовать запись
`self.__balance` без возбуждения исключений.

Вне тела класса такая автоматическая подстановка не работает. Выражение
`account.__balance` обращается к атрибуту с именем `__balance`, а такого
атрибута у объекта нет, поэтому возникает `AttributeError`.

С методами происходит то же самое:

```python
class Report:
    def build(self) -> str:
        return self.__format_title("sales")

    def __format_title(self, title: str) -> str:
        return title.upper()


report = Report()
print(report.build())                          # SALES
print("_Report__format_title" in dir(Report))  # True
report.__format_title("sales")
# AttributeError: 'Report' object has no attribute '__format_title'
```

### Name mangling не является защитой

Правило преобразования известно: `_ИмяКласса__имя`. Зная его, к атрибуту можно
обратиться из любого места программы:

```python
account = BankAccount(100)
account._BankAccount__balance = -500
print(account.get_balance())  # -500
```

Кроме того, присваивание `account.__balance = ...` вне класса не изменяет
атрибут, созданный внутри класса. Имя `__balance` вне класса не преобразуется,
поэтому создается **новый** атрибут:

```python
account = BankAccount(100)
account.__balance = 500
print(account.get_balance())  # 100 -- метод читает _BankAccount__balance
print(account.__dict__)       # {'_BankAccount__balance': 100, '__balance': 500}
```

Основное назначение name mangling — не запретить доступ, а **предотвратить
конфликты имен** между классом и классами, созданными на его основе
(наследование рассматривается далее в этом занятии). Побочным эффектом
является то, что обратиться к такому атрибуту снаружи становится сложнее.

### Имена с двумя подчеркиваниями с обеих сторон

Name mangling не применяется к именам, которые начинаются **и заканчиваются**
двумя подчеркиваниями. Такую форму имеют **специальные имена**, например
`__init__` и `__dict__`. Служебными в смысле этого конспекта они не являются.

Однако сами по себе подчеркивания не делают имя специальным: специальными
являются только имена, **смысл которых определен самим языком** и описан в
документации. Например, метод `__print_report__`, придуманный разработчиком,
интерпретатор считает обычным методом и самостоятельно не вызывает.

Тем не менее такая форма имен зарезервирована за языком, поэтому придумывать
собственные имена этого вида не следует: в новой версии Python такое имя может
получить специальный смысл.

## 5. Ответственность пользователя

Добросовестное использование публичного интерфейса — ответственность
пользователя. Он по-прежнему может обращаться к именам с префиксами `_` и `__`
(во втором случае достаточно указать преобразованное имя): интерпретатор этому
не препятствует. Например, для класса `BankAccount` из раздела 3:

```python
account = BankAccount("Alice")
account.deposit(100)
account._operations.append(-1000)  # выполняется без ошибок, но нарушает соглашение
print(account.get_balance())       # -900
```

Кроме обхода проверок, у такого обращения есть второе последствие. Разработчики
библиотеки обязуются поддерживать только публичный интерфейс: если изменить или
удалить метод `deposit`, перестанет работать код пользователей. Для деталей
реализации такого обязательства нет. Их можно переименовать, удалить или
изменить их смысл в любой новой версии.

Допустим, этот класс входит в библиотеку, а код
пользователя определяет количество операций по служебному списку:

```python
account = BankAccount("Alice")
account.deposit(100)
account.withdraw(30)
print(len(account._operations))  # 2
```

В новой версии библиотеки разработчики решили, что история операций не нужна, и
хранят только баланс:

```python
class BankAccount:
    def __init__(self, owner: str) -> None:
        self.owner = owner
        self._balance = 0

    def deposit(self, amount: int) -> None:
        self._check_amount(amount)
        self._balance += amount

    def withdraw(self, amount: int) -> None:
        self._check_amount(amount)

        if amount > self._balance:
            raise ValueError("insufficient funds")
        self._balance -= amount

    def get_balance(self) -> int:
        return self._balance

    def _check_amount(self, amount: int) -> None:
        if amount <= 0:
            raise ValueError("amount must be positive")


account = BankAccount("Alice")
account.deposit(100)
account.withdraw(30)
print(account.get_balance())  # 70 -- публичный интерфейс работает по-прежнему
print(len(account._operations))
# AttributeError: 'BankAccount' object has no attribute '_operations'
```

Код, который использовал только публичный интерфейс, изменений не заметит.
Код, который обращался к `_operations`, после обновления библиотеки перестанет
работать. Таким образом, используя детали реализации, пользователь рискует
потерять **обратную совместимость**: его код, работавший с предыдущей версией
библиотеки, не будет работать с новой.

Тот, кто обращается к служебному имени, берет ответственность за последствия на
себя. Редакторы и статические анализаторы могут предупреждать о таком
обращении.

## 6. Что использовать

| Вид имени | Пример | Смысл | Изменяется интерпретатором |
|---|---|---|---|
| без подчеркиваний | `balance` | часть публичного интерфейса | нет |
| одно подчеркивание в начале | `_balance` | деталь реализации, не использовать вне класса | нет |
| два подчеркивания в начале | `__balance` | деталь реализации, защищенная от конфликта имен | да: `_BankAccount__balance` |
| два подчеркивания с обеих сторон | `__init__` | форма, зарезервированная для специальных имен языка | нет |

Первые три вида имен имеют прямую аналогию со спецификаторами доступа C++:

| Имя в Python | Аналог в C++ |
|---|---|
| без подчеркиваний (`balance`) | `public` |
| одно подчеркивание в начале (`_balance`) | `protected` |
| два подчеркивания в начале (`__balance`) | `private` |

Различие в том, что в C++ доступ проверяет компилятор, а в Python можно
получить доступ к любому атрибуту.

На практике для служебных атрибутов и методов обычно используют **одно
подчеркивание**. Два подчеркивания применяют тогда, когда действительно нужно
исключить конфликт имен.

## Вывод

- **Инкапсуляция** объединяет состояние и поведение в объекте и скрывает
  детали реализации.
- **Публичный интерфейс** класса — атрибуты и методы, предназначенные для
  пользователя. Разработчик обязуется их поддерживать.
- Если все имена выглядят одинаково, пользователь не может отличить интерфейс
  от деталей реализации.
- Спецификаторов доступа в Python нет: все атрибуты доступны любому коду.
- Префикс **`_`** — соглашение, объявляющее имя служебным. Интерпретатор
  доступ не ограничивает.
- Префикс **`__`** включает **name mangling**: имя `__name` в классе
  `ClassName` заменяется на `_ClassName__name`. Это средство против конфликтов
  имен, а не защита от доступа.
- Специальные имена, например `__init__`, определены самим языком. Произвольное
  имя в двойных подчеркиваниях специальным не становится. Name mangling к
  именам такого вида не применяется.
- Соблюдать соглашения — ответственность пользователя. Поддержка деталей
  реализации не гарантируется, поэтому использующий их код рискует потерять
  обратную совместимость при обновлении библиотеки.
