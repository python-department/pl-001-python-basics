# LBYL и EAFP: два стиля обработки ошибок

> **Главная мысль.** Существуют два подхода к ситуациям, в которых операция
> может завершиться неудачей. **LBYL (Look Before You Leap — «посмотри, прежде
> чем прыгнуть»)** — подход, при котором условия выполнения операции
> проверяются с помощью `if` **до** ее запуска. **EAFP (Easier to Ask for
> Forgiveness than Permission — «проще просить прощения, чем разрешения»)** —
> подход, при котором операция запускается сразу, а возможное исключение
> обрабатывается в блоке `try-except`. Существует мнение, что EAFP — более
> характерный и предпочтительный для Python стиль работы с исключениями. Однако
> на практике выбор подхода зависит от **частоты возникновения исключений**:
> если операция в блоке `try` выполнилась без исключения, сам блок практически
> не замедляет программу, а проверка `if` в LBYL выполняется при каждом вызове.
> Если же исключение возникло, его создание и перехват заметно дороже проверки.
> Поэтому при редких исключениях EAFP не уступает LBYL и обычно быстрее, а при
> частых — быстрее LBYL. Неподходящий подход может заметно снизить
> производительность программы.

---

## 1. Два подхода на примере

Задача: получить цену товара из словаря; если товара в словаре нет, вернуть 0.

**LBYL** — сначала проверка, затем действие:

```python
def get_price_lbyl(prices: dict[str, int], product: str) -> int:
    if product in prices:
        return prices[product]

    return 0
```

**EAFP** — действие, затем обработка возможной ошибки:

```python
def get_price_eafp(prices: dict[str, int], product: str) -> int:
    try:
        return prices[product]

    except KeyError:
        return 0
```

Результат обеих функций одинаков. Различие в том, **когда** выявляется
проблема: в первом варианте — до обращения к словарю, во втором — в момент
обращения.

---

## 2. Недостатки LBYL

### 2.1. Гонки между проверкой и действием

Между проверкой и действием состояние может измениться. Это особенно важно
при работе с внешними ресурсами — файлами, сетью, другими процессами. Эту
ситуацию называют **TOCTOU (time of check to time of use)**:

```python
import os

path = "data.txt"

if os.path.exists(path):          # проверка: файл существует
    # здесь другой процесс может удалить файл
    with open(path) as file:      # использование: FileNotFoundError
        content = file.read()
```

Файл мог быть удален после проверки, поэтому `open` все равно может
возбудить исключение, и защита от него в любом случае нужна. EAFP не имеет
этой проблемы: проверка и действие объединены в одну операцию, и результат
сообщает само действие:

```python
try:
    with open(path) as file:
        content = file.read()

except FileNotFoundError:
    content = ""
```

### 2.2. Проверка неполна или дублирует логику

Условие проверки приходится формулировать самостоятельно, и легко упустить
часть допустимых или недопустимых значений:

```python
def parse_number_lbyl(text: str) -> int | None:
    if text.isdigit():
        return int(text)

    return None


print(parse_number_lbyl("42"))    # 42
print(parse_number_lbyl("-5"))    # None -- допустимое число отвергнуто
print(parse_number_lbyl(" 7 "))   # None -- int() допускает пробелы по краям
```

Метод `isdigit()` не описывает правила `int()`: он отвергает знак и пробелы,
которые `int()` принимает. Проверка воспроизводит часть правил самой операции,
причем неточно. В EAFP-варианте правила задает сама операция:

```python
def parse_number_eafp(text: str) -> int | None:
    try:
        return int(text)

    except ValueError:
        return None


print(parse_number_eafp("-5"))   # -5
print(parse_number_eafp(" 7 "))  # 7
```

### 2.3. Лишний код и повторная работа

LBYL может выполнять одну и ту же работу дважды: проверка `product in prices`
ищет ключ, а затем `prices[product]` ищет его снова. При сложных проверках
(например, разбор строки для проверки формата, а затем повторный разбор для
получения значения) затраты удваиваются.

---

## 3. Недостатки EAFP

- **Широкий `try` скрывает ошибки.** Если исключение может прийти не из той
  операции, которую защищает `try`, возможна неверная обработка (см. конспекты
  о `try-except` и `else`). Блок `try` должен быть минимальным.
- **Исключения дороже проверок**, если возникают часто (раздел 4).
- **Не для всех операций существует исключение.** Если операция не возбуждает
  исключение при неверных данных (например, срез за пределами списка тихо
  возвращает пустой список), без проверки не обойтись.
- **Часть действий необратима.** Если операция состоит из нескольких шагов и
  ошибка может возникнуть после того, как часть уже выполнена (например,
  записана половина файла), одной обработки исключения недостаточно: нужно
  либо проверить условия до начала операции, либо отменить уже выполненные
  шаги в обработчике исключения (откат).

---

## 4. Сравнение производительности

Скорость зависит от **частоты возникновения исключений**, потому что при
успешной и при неудачной операции подходы выполняют разный объем работы.

**Операция выполнилась успешно:**

- LBYL выполняет проверку `if` при каждом вызове, даже когда ошибки нет;
- EAFP не выполняет проверку, а блок `try` без исключения не добавляет заметных
  накладных расходов.

**Операция завершилась неудачей:**

- LBYL отвергает операцию проверкой `if`, исключение не создается;
- EAFP возбуждает и перехватывает исключение. Нужно создать объект исключения,
  собрать трассировку, найти обработчик и выполнить переход, поэтому это
  заметно дороже проверки.

Следовательно, EAFP выигрывает на каждой успешной операции и проигрывает на
каждой неудачной. Какой подход быстрее, определяет соотношение успешных и
неудачных операций.

Измерим обе стратегии при помощи `timeit` — модуля стандартной библиотеки для
измерения времени выполнения небольших фрагментов кода. Функция
`timeit.timeit(function, number=N)` вызывает переданную функцию `N` раз и
возвращает суммарное время в секундах:

```python
import timeit

present_prices = {"apple": 10}
missing_prices = {}


def get_price_lbyl(prices: dict[str, int]) -> int:
    if "apple" in prices:
        return prices["apple"]

    return 0


def get_price_eafp(prices: dict[str, int]) -> int:
    try:
        return prices["apple"]

    except KeyError:
        return 0


for title, prices in (("key present", present_prices), ("key missing", missing_prices)):
    for function in (get_price_lbyl, get_price_eafp):
        duration = timeit.timeit(lambda: function(prices), number=2_000_000)
        print(f"{title:12} {function.__name__:15} {duration:.3f} s")
```

Типичный результат (значения зависят от компьютера и версии Python; важны
только соотношения):

| Сценарий | LBYL | EAFP |
|---|---|---|
| Ключ есть | 0,125 с | 0,102 с |
| Ключа нет | 0,091 с | 0,386 с |

Выводы по измерениям:

- когда операция **успешна**, EAFP чуть быстрее или не медленнее LBYL,
  поскольку не выполняет проверку;
- когда операция **неудачна**, EAFP медленнее в несколько раз (в
  представленных измерениях примерно в 4 раза), потому что возбуждение и
  перехват исключения требуют больше работы, чем проверка.

### Зависимость от доли неудач

Решающий показатель — **доля операций, завершающихся исключением**. Чем реже
возникает исключение, тем выгоднее EAFP: проверка не выполняется, а затраты на
обработку исключения возникают редко. Чем чаще возникает исключение, тем выгоднее
LBYL: проверка дешевле возбуждения и перехвата исключения. Доля неудач, при
которой подходы сравниваются по скорости, зависит от операции, версии Python и
компьютера, поэтому универсального порога нет.

---

## 5. Когда что выбирать

**Выбирайте EAFP, если:**

- неудача — **редкая или исключительная** ситуация (файл обычно существует,
  ключ обычно есть, строка обычно корректна);
- операция работает с **внешними ресурсами** (файлы, сеть, база данных):
  проверка не гарантирует успеха из-за TOCTOU, а исключение все равно нужно
  обрабатывать;
- проверка **сложна, неполна или дублирует логику** самой операции (разбор
  числа, формата, даты).

**Выбирайте LBYL, если:**

- неудача — **частая или ожидаемая** ситуация (в данных много пропусков,
  значительная доля некорректных строк): исключения при высокой частоте
  заметно замедляют программу;
- проверка **проста и дешева** (`x in collection`, `len(items) > 0`,
  сравнение), а ее результат надежен;
- операция **не возбуждает исключение**, а возвращает некорректный результат
  (срез, `str.find` возвращает `-1`), либо исключение возникает слишком
  поздно, после частичных необратимых действий;
- после проверки не происходит гонки: данные принадлежат только этой
  программе и не меняются другими участниками.

Часто лучшим решением оказывается специализированный метод, в котором
проверка и действие объединены: `dict.get(key, default)`, `str.removeprefix`,
`os.makedirs(path, exist_ok=True)`.

## 6. Итоговое сравнение

| Критерий | LBYL | EAFP |
|---|---|---|
| Идея | проверить, затем действовать | действовать, затем обработать ошибку |
| Конструкция | `if` | `try-except` |
| Накладные расходы при успехе | проверка выполняется при каждом вызове | не добавляются |
| Накладные расходы при неудаче | только проверка | создание и перехват исключения |
| Гонки между проверкой и действием | возможны | не возникают, так как проверки нет |
| Дублирование логики проверки | часто | нет |
| Риск | неполная проверка | слишком широкий `try` |
| Подходит, когда | неудачи часты, проверка проста | неудачи редки, проверка сложна или ненадежна |

---

## Вывод

- **LBYL** проверяет условия перед действием (`if`), **EAFP** выполняет действие
  и обрабатывает исключение (`try-except`).
- У LBYL есть недостатки: гонки между проверкой и действием (TOCTOU),
  неполные проверки и дублирование логики операции.
- У EAFP есть риски: широкий `try` скрывает ошибки, а исключения дороже
  проверок.
- `try` без исключения практически не имеет накладных расходов; возбуждение и
  перехват исключения в несколько раз медленнее проверки `if`.
- Если неудачи редки, EAFP не медленнее LBYL; если неудачи часты, LBYL
  быстрее.
- Выбор определяется долей неудач, сложностью и надежностью проверки и
  характером ресурса. При наличии специализированного метода (`dict.get`,
  `exist_ok=True`) используется он.
